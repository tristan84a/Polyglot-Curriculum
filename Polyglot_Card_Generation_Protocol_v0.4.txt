POLYGLOT CARD GENERATION PROTOCOL

Version 0.2 Date: 2026-09-24

1.  Purpose

This protocol governs the mechanical and editorial process by which
Polyglot syllabi and cards are generated, checked, corrected, and
delivered. It complements the Polyglot Curriculum Charter and the
language syllabi.

The Charter governs how languages are taught. A language syllabus
governs what that language teaches and in what canonical order. This
protocol governs how those specifications are converted into syllabi and
card batches. Individual language curriculum CSVs contain authored
learning material. Learner scheduling state belongs separately to the
app/export and to the generated nine-column master CSV.

Curriculum specification and learner state remain separate.

2.  Source hierarchy and standard authoring operations

Polyglot has three standard ChatGPT authoring operations. Determine
which operation is being requested before deciding which files are
required.

A. CREATE A NEW LANGUAGE SYLLABUS

Use, in order:

1.  Polyglot Curriculum Charter.
2.  One or more existing approved language syllabi as structural and
    editorial models.
3.  Language-specific knowledge needed to design the new syllabus.
4.  This Card Generation Protocol for operational conventions.

The Charter is authoritative for system-wide pedagogy. Existing syllabi
are examples of scope, granularity, organization, and completion
standards; they are not templates that force another language into the
same grammatical sequence.

The output is a new versioned language syllabus. No card CSV or learner
state is required merely to design a syllabus unless reconciliation with
existing cards is part of the request.

B. BEGIN CARDS FOR A LANGUAGE

Use, in order:

1.  Polyglot Curriculum Charter.
2.  The new language’s approved syllabus.
3.  Curriculum manifest or other allocation record when needed to
    confirm the language’s ID block and initial frontier.
4.  Existing Polyglot_Master.csv, or representative established language
    curriculum CSVs, as examples of actual Polyglot card style and
    formatting.
5.  This Card Generation Protocol.

Polyglot_Master.csv is an example corpus for this operation, not
curriculum authority for the new language. It may demonstrate prompt
granularity, exact-match discipline, PartOfSpeech usage, InputHint
practice, and the way grammar is embodied in controlled examples.
French, German, or another existing language must not dictate the
structural sequence of a different language.

The output is that language’s six-column curriculum CSV:
ID,Language,EnglishPrompt,Target,InputHint,PartOfSpeech

C. EXTEND A LANGUAGE THAT ALREADY HAS CARDS

Use, in order:

1.  Polyglot Curriculum Charter.
2.  The relevant language syllabus.
3.  That language’s current six-column curriculum CSV.
4.  Current curriculum progress or manifest, where useful as a
    checkpoint or cross-check.
5.  This Card Generation Protocol.

The language CSV is authoritative for cards that actually exist and for
their canonical row order. Determine the current curriculum frontier
from the syllabus and existing cards, generate only what is still
needed, and continue with new stable IDs.

The full Polyglot_Master.csv is normally unnecessary for routine
extension of an established language because its scheduler fields do not
govern curriculum generation.

GENERAL SOURCE RULES

The curriculum manifest is a compact checkpoint and cross-language
index, not a mandatory input to every authoring operation. Use it when
it resolves ID allocation, syllabus version, frontier, or reconciliation
questions. The language syllabus and actual language CSV remain the
primary sources for routine continuation.

If a full syllabus has not yet been written for a language, safe early
cards may be generated from the Charter and established Polyglot models
only when explicitly requested. Do not pretend that an unwritten
syllabus exists in detail. If generation reaches a meaningful structural
fork that could affect many later cards, draft or clarify the relevant
syllabus portion before proceeding.

3.  Batch size and stopping point

A requested batch size is approximate unless the user explicitly
requires an exact count.

Prefer pedagogically coherent stopping points over round numbers. A
request for roughly 100 cards may therefore produce, for example, 85,
104, or 118 cards if that allows a unit or coherent subsection to finish
naturally.

Do not pad a completed unit merely to reach a target count. Do not
truncate a small amount of necessary coverage merely to avoid exceeding
it.

If a unit is too large to finish reasonably within the requested scale,
stop at a genuine internal pedagogical boundary and report that the unit
remains partial.

4.  Language-by-language generation

Prefer generating substantial runs for one language at a time.
Interlacing languages is a presentation or scheduling choice, not a
curriculum-design requirement.

For each language:

1.  Identify the lowest-numbered incomplete syllabus unit.
2.  Count existing valid cards toward its completion standard.
3.  Generate only the material still needed.
4.  Once the completion standard is met, advance to the next incomplete
    unit.
5.  Skip units already established, even if their cards were
    historically created out of canonical order.
6.  Preserve useful later material already present in the deck.
7.  Continue until a natural stopping point near the requested batch
    size.

Existing historical deviations are reconciled by convergence, not by
restarting the course.

5.  Completion standards, not quotas

Unit completion is determined by the syllabus completion standard, not
by a predetermined number of cards.

Card-count estimates are planning tools only. Generate the smallest
sufficiently varied set that makes the intended pattern established and
reusable.

A concept appearing once does not normally make it established.
Conversely, do not create redundant examples after the completion
standard has clearly been satisfied.

6.  Continuous vocabulary development

Vocabulary grows throughout grammar instruction.

When a grammatical pattern is new, keep lexical novelty restrained
enough that the pattern remains visible. As the pattern becomes
established, broaden vocabulary naturally.

Do not demonstrate many successive grammar units indefinitely with the
same tiny vocabulary. Do not introduce clusters of easily confused or
unnecessarily abstract new words merely to increase lexical variety.

7.  Card format

For generated curriculum material, the standard delivery contains only
the first six CSV columns:

ID,Language,EnglishPrompt,Target,InputHint,PartOfSpeech

Scheduler state is not generated as curriculum content. Weight, Active,
and LastShown belong to the app/export state and are supplied or
preserved separately.

CSV requirements: - UTF-8 with BOM when practical for Excel
compatibility. - Comma-delimited with standard CSV quoting. - Unicode
normalized consistently. - No duplicate EnglishPrompt within the same
language unless a future explicit schema change permits it. - InputHint
blank when unnecessary. - PartOfSpeech should use established Polyglot
categories such as noun, verb, adjective, adverb, phrase, sentence,
grammar, letter, script, or preposition.

8.  IDs

IDs are stable identifiers, not curriculum positions and not
presentation-order numbers.

Current convention for newly generated material uses integer language
blocks. French begins at 100000 and German at 200000. Additional
language blocks should be assigned deliberately and recorded before use.

Within a language block, assign new IDs monotonically and never reuse an
ID.

Do not encode syllabus unit numbers into IDs. A card may later be
reclassified under an amended syllabus without changing its stable
identifier.

Do not rely on ID order as the sole source of curriculum order. CSV row
order and the curriculum specification determine intended introduction
order.

If the integer block scheme ever approaches its reserved capacity,
expand the allocation scheme prospectively rather than renumbering
established cards.

9.  Prompt and answer design

Polyglot uses exact matching.

-   Each prompt has one intended Target string.
-   Case and diacritics are significant.
-   Leading and trailing whitespace are not pedagogical content.
-   EnglishPrompt should disambiguate meanings when ordinary English
    would permit materially different target answers.
-   Do not add multiple accepted answers merely to conceal an ambiguous
    prompt; improve the prompt instead.
-   Verbs normally use the dictionary or infinitive form for lexical
    cards.
-   Grammar should normally be taught through controlled examples rather
    than terminology questions.
-   Translation prompts are pedagogical mappings, not claims of
    permanent word-for-word equivalence.

10. InputHint

InputHint is an input-method field, not a pronunciation or
transliteration field. It is normally blank. Use it only when producing
the Target through the intended input method requires an intermediate
representation that cannot reasonably be inferred from the displayed
Target itself. Do not add InputHint merely because the writing system,
keyboard layout, pronunciation, or spelling is unfamiliar. Languages
entered directly in their own script therefore normally have blank
InputHint.

For phonetic/conversion IMEs such as those commonly used for Japanese
and Chinese, InputHint may give the practical input string required to
produce the Target. It remains post-answer guidance and is never an
alternative accepted Target.

11. Rule before exception

Teach productive or default patterns before exceptions and competing
constructions unless a very high-frequency irregular form is
pedagogically necessary earlier.

Keep the principal new pattern visible. Avoid mixing several new
grammatical mechanisms into the earliest examples of a unit.

Established grammar may be reused naturally in later cards.

12. Opportunistic audit of existing cards

While generating a language batch, inspect relevant existing cards
opportunistically.

If an existing card is clearly incorrect, materially unnatural for its
neutral English prompt, unnecessarily explicit or emphatic, misleading,
inconsistent with an established Polyglot convention, or superseded by a
better curriculum treatment, correct it when practical.

Do not launch a full retrospective audit of the entire language unless
requested. The purpose is to fix problems that become evident during
normal curriculum work.

Preserve the existing card’s stable ID and learner state when applying
such a correction to the master deck.

Example: if neutral Turkish “I drink.” is represented as “Ben içerim.”
and the explicit pronoun is not being taught or contrasted, “İçerim.” is
normally the preferable neutral target.

13. Reporting existing-card corrections

Every modification to a pre-existing card must be explicitly reported in
the batch summary.

Report the card ID, old prompt or target as relevant, new prompt or
target, brief reason, and confirmation that learner state is to be
preserved when the correction is merged.

Never silently alter existing cards.

14. Script and orthography

Follow each language’s established script policy.

Finite script bootstraps should remain finite. Ordinary language cards
should move to direct target-script use when the syllabus specifies that
transition.

Kanji or other large literacy systems may develop continuously alongside
vocabulary rather than being treated as one finite alphabet lesson.

Do not impose a universal script-learning method across structurally
different writing systems.

15. Existing later material

Historical cards may contain material from units later than the current
curriculum frontier.

Such cards remain valid if linguistically and pedagogically sound. Count
them when their unit is audited. Do not regenerate them merely because
they appeared early.

Incidental exposure does not automatically equal establishment. Apply
the syllabus completion standard.

16. Validation before delivery

Before delivering a batch, verify at minimum:

1.  Every new ID is unique.

2.  No new ID conflicts with supplied existing data.

3.  EnglishPrompt is unique within the language under the current
    schema.

4.  Required CSV columns are present and in the agreed order.

5.  Targets use correct spelling, capitalization, diacritics,
    punctuation, and script.

6.  InputHint follows the language’s established convention.

7.  Card order follows prerequisite-aware curriculum progression.

8.  No unit is declared complete without satisfying its completion
    standard.

9.  Existing-card changes, if any, are intentional and separately
    reported.

10. The batch stops at a defensible pedagogical boundary.

11. Batch summary

Each delivered batch should briefly state the number of new cards, ID
range, syllabus units completed, any unit left partial, the next
curriculum unit, important vocabulary or script decisions, every
correction to an existing card, and any unresolved issue requiring user
judgment.

The summary should describe curriculum progress rather than merely
repeat file statistics.

18. Curriculum files, master file, and learner state

Individual language curriculum CSVs are the canonical authored card
files. They normally contain only:

ID,Language,EnglishPrompt,Target,InputHint,PartOfSpeech

Polyglot_Master.csv is a generated operational file used by the app. It
combines the language curriculum files and adds:

Weight,Active,LastShown

These scheduler fields are not authored by ChatGPT during curriculum
generation.

When rebuilding Polyglot_Master.csv, preserve Weight, Active, and
LastShown from the latest app export or state file by stable card ID.
Initialize those fields only for genuinely new IDs, normally as
Weight=100, Active=true, LastShown blank.

A merge must not attach learner state to a different card merely because
an ID was reused or reassigned. If an existing stable ID now points to a
different language, EnglishPrompt, or Target, treat that as a conflict
requiring review rather than silently transferring state.

The merger must preserve the canonical row order within each language
curriculum file. Cross-language file ordering is an operational choice
and must not alter the internal curriculum sequence of a language.

ChatGPT should not edit scheduler state while creating or extending
curriculum. Existing-card curriculum corrections preserve the card’s
stable ID; the merge process then preserves its learner state.

19. Amendments

This protocol is versioned.

Routine card generation changes curriculum progress, not this protocol.
Amend the protocol only when the generation process itself changes.

Future amendments should be recorded explicitly so that new
conversations do not depend on reconstructing operational rules from
chat history.

Version 0.2 formalizes three standard authoring operations: creating a
new language syllabus, beginning cards for a new language, and extending
an existing language. It also formalizes the separation between
six-column language curriculum files and the generated nine-column
Polyglot_Master.csv, including preservation of learner state by stable
card ID during merging.

20. Governing principle

Curriculum decisions belong in the Charter and syllabi. Generation
mechanics belong in this protocol. Progress belongs in the manifest and
card data. Learner scheduling state belongs in the app or export.

Keep those concerns separate whenever practical.
